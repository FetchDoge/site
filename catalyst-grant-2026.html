1THE PROBLEM

Institutions — universities, publishers, funders, labs — want AI agents working inside real research workflows: evidence synthesis, manuscript screening, reviewer matching, data processing. Today they face a binary choice: keep agents away from anything consequential, or deploy them with guardrails that were never designed for agency — prompt-level instructions ("do not do X"), post-hoc log review, content filters. Prompt instructions fail silently; logs are reviewed after the damage. The result is automation value left on the table (reviewer hours, editorial time, synthesis labor) on one side, and unquantified tail risk on the other: an unaudited agent action against live data, a compliance breach, an erroneous step in a publication pipeline. This decision — can we trust an agent with this workflow? — comes up with every agentic deployment an institution considers, weekly across a sector that runs thousands of such decisions a year.

2YOUR WORKFLOW

Interlock is a zero-dependency Python substrate that sits between the agent loop and its tools — not a separate application, a layer the agent runs through. Step by step: (1) The operator issues authority leases — scoped, expiring grants naming exactly which tools the agent may call, with which arguments, for how long. (2) The agent plans and requests tool calls as normal. (3) Interlock checks every call against the live lease: in-scope and unexpired, it executes; anything else is denied, and the denial is logged. (4) Every executed action emits a provenance-stamped claim — its authorizing lease, provenance, timestamp, review date, and falsifier. (5) A fault bus aggregates anomalies — repeated denials, lease expirations, unexpected patterns — and can trip a global e-stop that freezes all agent action instantly. (6) A person reviews the claim ledger, renews or narrows leases, and releases the e-stop. Autonomous steps: tool execution inside a valid lease. Human steps: lease issuance, e-stop release, claim review. It wraps the tool-call boundary of any Python agent loop — the team's existing runtime, not a new platform. Today it is used by its solo developer; it is designed to embed in institutional agent deployments.

3TRUST, AUDIT AND GOVERNANCE

A user sees what the agent did by reading the claim ledger: every action recorded with its authorizing lease, timestamp, and outcome — no reconstruction from scattered logs. Provenance is stamped at execution time: each claim states what produced it, under what authority, when it was valid, and what would prove it wrong. When the agent is uncertain or wrong, the failure mode is denial, not improvisation: an out-of-lease call is refused and logged; escalating anomalies trip the e-stop. Accountability is structural: every claim names the lease issuer — authority is always attributable to a person, never diffused into "the agent decided." We also test where it breaks: denial-path tests cover expired leases, engaged e-stop, and fault-gated resources, so refusal is exercised in CI rather than asserted.

6ALTERNATIVES AND COMPETITORS

How it is solved today: prompt-level instructions, output validators, post-hoc log review — or the null option, keeping agents out of consequential workflows entirely. Who else is working on it: the space is active. Microsoft's Agent Governance Toolkit (policy-as-code; github.com/microsoft/agent-governance-toolkit), Guardrails AI (output validation; github.com/guardrails-ai/guardrails), NVIDIA NeMo Guardrails (programmable conversation rails; github.com/NVIDIA-NeMo/Guardrails), OpenAI's AgentKit guardrails and Agents SDK guardrail hooks, and pre-action authorization plugins such as APort's. How we are different: most of these are framework-specific, content-focused (what the model says), or policy layers bolted beside the agent. Interlock is a zero-dependency substrate at the tool boundary — expiring authority leases, a global e-stop, a fault bus, and provenance-stamped claims — framework-agnostic, with accountability naming a human lease issuer rather than just filtering content.
